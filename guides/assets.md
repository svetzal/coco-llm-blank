# Prepare assets before the drawing loop

Read this when deciding how a game's artwork becomes reusable drawing data.
The examined sources are CoCo 3 community articles. The original proposals
have a bounded [host preparation check](../guidance/asset-validation.md)
with 33 passing cases. Target integration and banked storage remain untested.
Their general data-design ideas can inform CoCo 1/2 work,
but neither source establishes a CoCo 1/2 implementation.

Use [animation storage](animation.md) for packed-size calculations and
[moving objects](moving-objects.md) for the renderer and background policy.
This guide addresses the earlier step: what the renderer receives, when the
picture is prepared and where its bytes live.

## Separate source art, prepared pictures and scene state

Diego Barizo's "Mine Sweeper! The Mission", *CoCoNutz!* volume 2, issue 2,
July 2006, PDF 12–19, draws artwork during setup, captures HGET buffers and
selects them while displaying its map. Read graphics setup 4500–4960 and map
drawing 5000–5070, PDF 17–18. This is a BASIC workflow, not a documented
binary asset format. [Source][barizo]

Our proposed assembly workflow is:

1. Create original source art or a deterministic drawing recipe.
2. Prepare each picture once, on the host or during loading. Record dimensions,
   row stride, packing, palette identity and any mask separately.
3. Give each prepared picture an asset ID. Keep terrain and actor state in
   their own structures; translate those values to asset IDs explicitly.
4. Let the drawing loop consume prepared pictures. Keep generation and file
   parsing out of that loop until measurements justify their cost.

Host preparation makes generated bytes repeatable but requires a tracked
converter and source assets. Runtime generation reduces stored artwork only
if the recipe and its drawing machinery cost less; it adds startup work and
still needs storage for the prepared pictures. Neither saving is measured here.
Barizo's use of random marks is not a deterministic reference image without
control of its random input.

An original interface sketch, not runnable code:

```text
prepare_level(level):
    pictures = prepare_original_art(level.art, fixed_seed)
    validate_dimensions_and_storage(pictures)
    validate_asset_ids(level.terrain_to_asset, pictures)
    publish(pictures)

draw_cell(cell):
    asset_id = terrain_to_asset[cell.terrain]
    draw_prepared(pictures[asset_id], cell.screen_origin)
```

Reject invalid IDs before publishing the level. Do not silently turn a missing
asset into terrain zero. Treat picture pixels, transparency, collision shape
and terrain rules as different concepts.

## Make coordinates and palette ownership explicit

Barizo's prose says map numbers match buffer numbers, but line 5050 uses
`M(X,Y)+1`. His terrain and cursor use different coordinate offsets. Those
are concrete reasons to define an ID translation and an anchor for each asset,
not to copy the prose into a renderer contract. [Barizo, PDF 12–14, 18][barizo]

For our proposed asset descriptor, name width, height, origin offset, row stride
and palette ID. An asymmetric test picture should distinguish top from bottom
and left from right. Use inclusive or exclusive bounds consistently in your
own format; do not infer a packed-byte layout from BASIC's HGET syntax.

The same article's introduction consumes text DATA before palette DATA. Even
its skip path reads to a sentinel. Our adaptation gives palette and text
independent offsets and lengths, so skipping text cannot shift the palette
reader. Select the display contract using [colour guidance](colour.md).
Barizo specifies RGB and points TV users to different palette data; that is
not evidence of equal appearance on both displays. [PDF 12, 18–19][barizo]

## Distinguish stored banks from the accessible window

Robert Gault's "Special Backup Utility for a Coco3 Using Full 512K RAM",
*CoCoNutz!* volume 2, issue 3, October 2006, PDF 38–46, accesses bulk disk data
through a mapped window. Read `MMU` on PDF 41, `RDWRDK` on PDF 44–46 and
`COLD` on PDF 40–41. The tutorial requires a 512K CoCo 3; it is not a game
loader. [Source][gault]

Our proposed asset descriptor for a banked implementation records a storage
block and offset, not only a CPU pointer. A pointer becomes stale when another
block replaces its window. Before using this design:

1. Reserve blocks for assets, code, state, stack and display independently.
2. Choose either copying assets into a stable draw buffer during level loading,
   or mapping them for each bounded access. Copying costs RAM and transfer
   work; mapping requires control of every user of that window.
3. Keep code, stack and required interrupt data accessible during the operation.
   Check the actual target's MMU and interrupt references before writing code.
4. Restore the caller's mapping on success and failure, or document exclusive
   ownership for the whole phase. Gault's BASIC restoration constant is not
   a general save-and-restore interface.

A game with concurrent sound needs additional evidence. The backup tutorial's
interrupt handling does not prove that a frame loop and sound handler can share
its mapping policy. Do not infer a safe remapping sequence from this guide.

## Require evidence before adding compression or frame tables

Neither selected article specifies a compressed picture format or a timed
animation-frame table. Do not label HGET capture as compression. Start with
an explicit uncompressed format and account for headers, masks, palette data,
working buffers and any shifted variants.

For a later codec proposal, require both encoded and decoded lengths, reject
truncation and output overflow, and measure worst observed decode cost on the
chosen target. A small file can still need a large working buffer. These are
original design requirements, not results from either article.

## Proposed checks before implementation is called working

No checks in this table were executed in this source-only pass.

- Asset ID lookup. Distinct terrain IDs select distinct original pictures.
  Remove the translation entry; loading must fail before drawing.

- Pixel preparation. An asymmetric hand-calculated fixture matches expected
  bytes. Reverse row order or swap two palette indices; comparison must fail.

- Text and palette loading. Full introduction and skipped introduction produce
  the same palette. Truncate the palette section; reject it without publishing
  partial assets.

- Coordinate anchor. Terrain and cursor land at independently specified
  positions. Reuse the cursor anchor for terrain; expected image must detect
  displacement.

- Bank access. Two blocks at the same window return different known fixtures.
  Deliberately reuse a pointer after remapping; the check must detect stale
  identity.

- Mapping restoration. A completed load restores the prior mapping. Inject an
  error midway through loading and check restoration and guards.

Keep host-format tests, target assembly, emulator execution, framebuffer,
rendered output and physical-machine evidence separate. The tracked
[host experiment](../experiments/assets/README.md) checks fixed RG6 preparation
and publication. Target loading and banked-storage checks remain proposals.
