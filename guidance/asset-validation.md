# Original host asset preparation validation

Question: can a small original asset converter validate terrain references and
picture geometry, produce deterministic RG6 bytes, and reject bad or stale
input/output before a caller treats it as a prepared room?

The runnable [experiment](../experiments/assets/README.md) implements the host
preparation proposal in [the asset guide](../guides/assets.md). It matches the
existing CoCo 1/2 tile-room layout, but does not replace its art, alter its
assembly or establish target execution with these generated bytes.

## Sources and original decisions

Before implementation, this pass read the asset guide, its complete
[community research record](community-game-research.md), the tile-room layout
and its source notes. It also inspected these local primary-source page images:

- Don Inman, Kurt Inman with Dymax, [Assembly Language Graphics for the TRS-80
  Color Computer][graphics], PDF 107, printed 98. Eight graphic elements per
  byte; colour set zero is 0 black, 1 green. Local PDF SHA-256 recorded by the
  tile-room reading is
  `c1259497b7d1505e6908fd3c8a250d47e0c4b549140e308bdc6bf8e345b6ce01`.
- Motorola, [MC6847 datasheet][vdg], PDF/printed 19, Table 3. RG6 has 256×192
  elements and 6,144 display bytes, with left-to-right L7 through L0. Local PDF
  SHA-256 recorded by the tile-room reading is
  `2d4586d2fd3c82c60071bbe4cc3930e561c00dce1e43245b0c7ffd5e081fe88c`.

The 32-byte screen stride follows from 256 / 8. The 8×8 picture dimensions,
room arrangement and upper-left placement follow the existing
[tile-room contract](../examples/tile-room/README.md#target-and-layout).
No register setup is implemented here.

The community guide attributes preparation and later picture selection to
Diego Barizo's "Mine Sweeper! The Mission", *CoCoNutz!* volume 2, issue 2,
July 2006, PDF 12–19, specifically setup 4500–4960 and map drawing 5000–5070.
Its research record notes that line 5050 translates map values with `+1` and
uses different terrain/cursor offsets. This pass uses that recorded reading
as design motivation, not as a newly verified historical execution result.
The article describes CoCo 3 BASIC HGET, not the format implemented here.
Exact URLs, hashes and reading limits remain in the linked research record.

All converter code, tests and four pixel drawings are original to this
experiment. No historical code or artwork was copied. The room arrangement
comes from this repository's original tile-room example. Sparse asset IDs,
strict fixed dimensions, canonical JSON and fail-closed publication are our
implementation choices. The source articles do not establish them as a
historical format. No compression or bank-loader proposal is implemented.

## Independent expectations and controls

The spec contains four manually calculated byte strings. For example, the
wall's rows are `ff 80 b8 a0 ae 82 80 fd`; its third row `10111000` has weights
128 + 32 + 16 + 8 = 184, hex `b8`. These constants are not generated by the
packer. Every packed picture must equal its literal and decode back to every
original source pixel. The decoder expands binary strings rather than using
the converter's shift-and-sum operation.

A second oracle constructs a full 256×192 pixel matrix. It uses literal wall,
collectible and exit coordinates and literal asset IDs rather than reading the
source map or mapping table for its expectations. It compares all 49,152
pixels, including the unused screen. Separate assertions cover the last cell,
the exit's bottom row and the first row outside the room.

Executed controls cover:

- Reversing bits in each screen byte, reversing picture rows and complementing
  palette indices. Each differs from the independent expectation.
- Swapping two valid mapping entries. Validation permits this intentional art
  assignment, but the independently specified scene detects the wrong picture.
- Moving the composed screen down one pixel or right one byte. The scene oracle
  detects displacement. Nonzero source anchors are rejected separately.
- Missing or duplicate asset IDs, missing mappings, negative and oversized
  terrain IDs, negative asset IDs, wrong dimensions/stride, ragged pixels/maps,
  out-of-range pixels, Boolean/float pixels, wrong packing/palette and extra
  fields. Each fails with no output, both on first build and after stale output.
- Missing input and malformed JSON, plus source/output path collision.
- Repeated builds, changed source, stale and truncated output, missing output,
  and successful rebuilding after stale rejection.
- CLI build/check, help, invalid action and a missing-output error.

The controls intentionally damage inputs or results and require detection.
They do not claim that a decoder round-trip alone proves correct packing.
The scene oracle shares the source pixels, but the independent literal byte
fixtures prevent a matching encoder/decoder error from certifying those pixels.

## Executed evidence and limits

The scoped run on 2026-11-14 used Python 3.13.12 and passed 33 specs. Combined
statement and branch coverage of `experiments/assets/prepare.py` was 97.52%.
The scoped coverage configuration requires at least 90%; it does not include
unrelated starter scripts. Scoped Ruff lint/format and Markdown lint passed.
The real CLI build and check commands also passed against a temporary output.
Six regression cases reject Boolean and floating-point width, height and stride
through both CLI commands. Geometry requires integers before fixed bounds are
checked. Invalid builds remove stale output; failed checks leave it untouched.
See the experiment README for exact repeat commands.

This is host-format and filesystem validation only. There is no new assembly,
CoCo emulator execution, framebuffer capture from a target, rendered-display
inspection or physical-hardware evidence. The computed framebuffer is a host
oracle artifact. It is not a captured screen. Existing tile-room target results
do not transfer to this new converter or its artwork.

CoCo 3, PAL/T1 display behaviour, composite artifact colours, actor drawing,
collision, masks, arbitrary tile sizes, scrolling, sound and bank switching
are outside this experiment. No target memory, startup time, frame rate or
hardware performance claim follows. Fault injection during filesystem writes,
concurrent writers and power loss were not tested. No target check is planned
in this scoped task. Integration requires a separate target consumer and checks.
